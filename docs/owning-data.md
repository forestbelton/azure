# Owning an overlay's data in C

How to turn

    extern char D_80027F20[];

into

    char D_80027F20[16] = "BASLUS-00614";

and have splat, the generated linker script and the container all agree.

Everything below was measured on 2026-11-08 against `data/main/main.bin`
(sha1 `69f63236b7ab2260e2e9aa2048ce7aa540bdbe6d`) with splat 0.50.1 /
spimdisasm 1.42.4, taking `csrc/ovl_main_80020000.c` from `extern` to owning
`D_80027F18` and `D_80027F20`. All four containers stayed byte-identical.
Re-measure rather than trust.

This is about **data**. Code is `docs/landing-a-function.md`; rodata needs none
of this, because splat migrates rodata per symbol and the `INCLUDE_RODATA`
stubs at the foot of `csrc/ovl_main_80020000.c` are already that mechanism.

---

## 1. Why data is the awkward one

splat has three different stories for the three section kinds, and the
difference is the whole reason this document exists.

| section | dotted subsegment writes | per-symbol ownership? |
|---|---|---|
| `.rodata` | the symbol into the referencing function's `asm/nonmatchings/.../*.s` listing | **yes** -- replace one `INCLUDE_RODATA` at a time |
| `.text` | one `.s` per function under `asm/nonmatchings/` | **yes** -- replace one `INCLUDE_ASM` at a time |
| `.data` | **nothing at all** | **no** |

That last row is the constraint. `splat/segtypes/common/data.py`'s
`should_self_split()` returns `False` for a type that starts with a dot, and
`common/c.py`'s migration loop only ever looks at `.rodata` and `.rdata`. So a
`- [addr, .data, unit]` subsegment emits no assembly and no stub: **the C unit
must define every byte of that subsegment's span, or those bytes vanish from
the container.**

And there is exactly **one** such span per unit. `parse_subsegments()` keys
siblings by linker section (`sibling.siblings[".data"] = segment`), so two
`.data` subsegments named after the same C unit would both resolve to
`build/csrc/<unit>.o(.data)` and link the same section twice. One unit, one
contiguous owned window.

The way out is to carve the data region into **a `.data` subsegment for the
window you own and ordinary undotted `data` subsegments for the rest**. An
undotted `data` subsegment keeps getting disassembled, into
`asm/data/<name>.data.s`, which the existing `build/%.o: %.s` rule assembles
with no Makefile change. Its name has to differ from the C unit's, or splat
makes it a sibling and you are back to the double-link.

---

## 2. How a name gets its address

Four links in the chain. Know which one you are changing.

**`splat/main.bin.yaml`** is the only source of truth for which object owns
which address range. Everything else is generated from it.

**`build/main.bin.ld`** is generated by `splat split`. With
`ld_legacy_generation: True` it emits one input-section line per subsegment,
**in subsegment order**, grouped into the segment's `.rodata` / `.bss` /
`.text` / `.data` blocks. For the 0x80020000 overlay:

```
    ._25D000 0x80020000 : AT(_25D000_ROM_START) SUBALIGN(4)
    {
        _25D000_RODATA_START = .;
        build/csrc/ovl_main_80020000.o(.rodata);
        ...
        _25D000_TEXT_START = .;
        build/csrc/ovl_main_80020000.o(.text);
        ...
        _25D000_DATA_START = .;
        build/asm/data/ovl_main_80020000_data_pre.data.o(.data);
        build/csrc/ovl_main_80020000.o(.data);
        _25D000_DATA_END = .;
    }
```

Note that `build/csrc/ovl_main_80020000.o(.data)` was in this script **before
any of this work**, with no `.data` subsegment in the yaml at all. splat's
`auto_link_sections` inserts a generated sibling for each missing section of a
C unit and places it after the unit's text. That is why a C-defined data object
lands at the right address almost for free -- and it is also the trap: the
generated entry sits *before* any explicit `data` subsegment you add, so if you
add an undotted `data` chunk and no explicit `.data`, the C unit's data is
placed first and your asm chunk's symbols all shift. **List both subsegments
explicitly, in address order.**

**`splat/main.bin_undefined_syms_auto.txt`** is the "not owned by anything"
list -- a linker script of absolute assignments, `D_80027F20 = 0x80027F20;`,
passed with `--script=`. `write_undefined_syms_auto()` emits every symbol that
is `referenced` and not `defined`. A symbol inside any subsegment, dotted or
not, is `defined`, so adding the subsegment is what drops the line. You never
edit this file; it is regenerated on every split.

**The C file itself** decides the order. cc1psx lays `.data` objects out in the
order they are written, so **definition order is address order**. A new object
goes at its address position in the `.data` block at the foot of the unit and
nowhere else.

ROM-to-vram for this overlay: `vram = 0x80020000 + (rom - 0x25d000)`.

## 3. From a vram address to a splat offset

Everything in `splat/main.bin.yaml` is addressed by **rom offset into the
container**, never by vram. The only thing that carries a vram is the `code`
segment's own `vram:` key, and every subsegment under it gets its address
implicitly from its offset. So the first thing you do with an address like
`0x80027F18` is convert it.

The conversion is a single affine map, fixed per segment by the `start:` /
`vram:` pair at the top of that segment:

```
rom  = vram - segment_vram + segment_start
vram = rom  - segment_start + segment_vram
```

For main.bin's low overlay, `start: 0x25d000` and `vram: 0x80020000`:

```
rom = 0x80027F18 - 0x80020000 + 0x25d000
    =     0x7F18            + 0x25d000
    = 0x264F18
```

That is the number you write in the yaml, and it is also the number splat
prints in the left-hand column of every disassembly comment, which is the
cheapest way to confirm you got it right:

    /* 264F18 80027F18 7C000280 */ .word 0x8002007C
       ^rom   ^vram

The four containers each have their own map, and they are not
interchangeable -- `0x80027F18` is only an overlay address because
`main.bin`'s overlay is loaded at `0x80020000`:

| segment | `start:` | `vram:` | `rom = vram - delta` |
|---|---|---|---|
| `main.bin` low overlay | `0x25d000` | `0x80020000` | `vram - 0x7FDC3000` |
| `main.bin` debug twin | `0x269000` | `0x80400000` | `vram - 0x80197000` |
| `town.bin` overlay | `0xb000` | `0x80088760` | `vram - 0x8007D760` |
| `dungeon.bin` overlay | `0xa3000` | `0x80088760` | `vram - 0x7FFE5760` |

A one-liner, so you are not doing hex by hand:

```sh
# usage: v2rom 80027F18
v2rom() { python3 -c "print('0x%X' % (int('$1',16) - 0x80020000 + 0x25d000))"; }
```

Three sanity checks before you trust a number:

* **It must lie inside the segment.** The low overlay is
  `0x25d000..0x269000`, i.e. vram `0x80020000..0x8002C000`. An address outside
  that is not this overlay's and does not belong in this yaml at all -- see
  `docs/addressing-and-translation-units.md` on the out-of-image
  constant-base-pointer globals, which look like overlay addresses and are not.
* **The bytes must be what you expect.** `xxd -s 0x264f18 -l 0x10
  data/main/main.bin` should show the words you are about to write into C.
* **splat must already agree.** The address appears verbatim as the second
  column of the generated listing, or as
  `D_80027F18 = 0x80027F18;` in `splat/main.bin_undefined_syms_auto.txt`. If
  your computed offset's listing line shows a different vram, the segment's
  `vram:` is not the one you used.

One more place the same map shows up: the auto-generated symbol names. splat
names an unknown data symbol `D_<vram>`, so `D_80027F18` *is* its address in
hex and no conversion is needed to go the other way -- strip the `D_` and
subtract.

## 4. The procedure

Worked against `D_80027F20` at vram `0x80027F20`, rom `0x264f20`.

### 4.1 Find the object's real span

The upper bound is the next symbol's address, and the authority on where one
object ends and the next begins is splat's own disassembly. If the range is
still an undotted `data` subsegment, read its `dlabel` / `enddlabel` pairs:

    sed -n '/dlabel D_80027F18/,/enddlabel/p' asm/data/ovl_main_80020000_data_pre.data.s

If it is still a `bin` blob, read the bytes and the next referenced symbol:

    xxd -s 0x264f20 -l 0x20 data/main/main.bin
    grep -n 80027F data/../splat/main.bin_undefined_syms_auto.txt

`D_80027F20` runs to `D_80027F30`, so the span is **0x10 bytes** -- twelve
characters, a NUL, and three bytes of padding that belong to the object.

### 4.2 Move the subsegment boundary in the yaml

Carve the data region so the object you are claiming falls inside the C unit's
`.data` window and everything else stays in an undotted `data` subsegment or a
`bin` segment:

```yaml
  - type: code
    start: 0x25d000
    vram: 0x80020000
    subsegments:
      - [0x25d000, .rodata, ovl_main_80020000]
      - [0x25d924, c, ovl_main_80020000]
      - [0x264e20, data, ovl_main_80020000_data_pre]   # not yet owned
      - [0x264f18, .data, ovl_main_80020000]           # owned by the C unit
  - [0x264f30, bin]                                    # not yet owned
```

The window grows in **either** direction, one contiguous range:

* **down** -- lower the `.data` start, and `_data_pre` shrinks to match.
* **up** -- raise the `.data` end, which means raising the start of whatever
  segment follows (here the `bin` at `0x264f30`). Both boundaries are
  hand-maintained and both have to track the C file.

Shrinking a `bin` segment leaves its extracted blob behind. `OFILES` is built
from `find assets -name '*.bin'`, so the orphan keeps getting assembled into an
unreferenced object:

    rm -f assets/main/264E20.bin build/assets/main/264E20.o

### 4.3 Re-split

    splat split splat/main.bin.yaml

That rewrites `build/main.bin.ld`, the `undefined_*_auto.txt` pair and any
`asm/data/*.data.s`. It is the same command the `build/%.ld: splat/%.yaml` rule
runs, so a plain `make` would do it too.

**Do not add `--modes ld`.** It produces the linker script but *empties* both
tracked `undefined_*_auto.txt` files, because the symbol-collection pass is
skipped. **And never `rm -rf build`** -- `build/main.bin.ld` is generated and
`expected/build/` holds a stale copy. Both traps are written up in
`docs/town-sweep.md`.

`make splat` also works but wipes `asm/nonmatchings` and re-splits all four
yamls, which you do not need.

Check that splat agreed with you:

    git diff --stat splat/
    # splat/main.bin_undefined_syms_auto.txt should have LOST exactly the
    # symbols now inside the .data window, and nothing else.

### 4.4 Define it in C

At the foot of `csrc/ovl_main_80020000.c`, in address order:

```c
char *D_80027F18[2] = {
    (char *)D_80020074 + 8,
    (char *)D_80020074,
};

char D_80027F20[16] = "BASLUS-00614";
```

* **Write the size explicitly.** `[16]`, not `[]`. See §6.
* **Keep the declaration in the header** if any use site is above the
  definition -- which it almost always is, since the definition has to sit at
  its address position at the foot of the file. A header declaring a symbol its
  own translation unit defines is ordinary C, and the sized `extern` earns its
  keep: `extern char D_80027F20[16];` against a `char D_80027F20[12]`
  definition is a hard `conflicting types` error, which is one more gate for
  free.
* **Pointers are fine.** A pointer initialiser comes out as `R_MIPS_32` with
  the addend in the section, and ld resolves it to the same absolute word the
  original holds. `(char *)D_80020074 + 8` reaches the `"bu00:"` that shares
  `D_80020074`'s migrated rodata listing with `"bu10:"`; measured, both
  relocations land and the four words match byte for byte.

## 5. Verification -- and the gate `make` does not give you

Run, in order:

    make build/main.bin                     # the container
    mips64-linux-gnu-nm build/main.bin.elf | grep -E "_25D000_DATA_(START|END|SIZE)"

`_25D000_DATA_END` must equal the vram of the segment that follows the data,
`0x80020000 + (next_rom - 0x25d000)`. With the `bin` at `0x264f30` that is
`0x80027F30`, and `_25D000_DATA_SIZE` is `0x110`.

**`make` alone will not catch a short object.** Measured: declaring
`D_80027F20[12]` -- four bytes short -- still built `main.bin` **byte-identical**,
because the segment ends on `__romPos = ALIGN(__romPos, 16)` and `objcopy`
zero-fills the gap, which happens to be exactly the three padding bytes the
object dropped. The only symptom was

    80027f2c T _25D000_DATA_END      # should be 80027f30
    0000010c A _25D000_DATA_SIZE     # should be 00000110

The error does not bite until the *next* object you claim, which then starts
four bytes low and shifts everything after it. Check `_25D000_DATA_END` after
every landing.

Also worth a look once:

    mips64-linux-gnu-nm build/main.bin.elf | grep ' D_80027F20$'   # 80027f20
    mips64-linux-gnu-objdump -s -j .data -r build/csrc/ovl_main_80020000.o

Then the real gate, because `OFILES` is shared and a yaml edit can move a
boundary in a container you were not thinking about:

    make containers

All four must come out byte-identical.

## 6. Measured facts and traps

* **cc1psx pads a data object up to its own alignment, and no further.**
  `char D_80027F20[] = "BASLUS-00614";` emits `.ascii "BASLUS-00614\000"`
  followed by `.space 3` -- 16 bytes, which is right *here* only because
  `align(13, 4) == 16`. An object whose true span is not `align(strlen+1, 4)`
  comes out short with `[]`. Write the size.

* **`data` vs `.data` is not cosmetic, and neither is the name.** Undotted
  `data` disassembles to `asm/data/<name>.data.s`; dotted `.data` writes
  nothing and hands the span to the C sibling. The undotted chunk's name must
  differ from the C unit's. This is the same dot rule as `.rodata` in the same
  yaml, seen from a third side -- the comments on all three subsegments in
  `splat/main.bin.yaml` are worth reading together.

* **One `.data` subsegment per unit.** If you need two disjoint owned ranges,
  carve the translation unit instead -- `docs/overlays.md` already has the
  nine-source boundaries (`c_server.c`, `card_mes.c`, ... `memory.c`) this
  overlay should eventually split along, and each of those units gets its own
  window. Remember `build/csrc/ovl_%.o` is the pattern rule that gives an
  overlay unit its `-G0`; a new unit outside that prefix silently gets the
  resident flags.

* **Order the subsegments explicitly.** Relying on `auto_link_sections` to
  place the C unit's `.data` works only while there is no undotted `data`
  chunk; the generated entry goes right after the text, i.e. *before* the chunk
  you wanted first.

* **`defined:True` in `splat/main.bin_symbol_addrs.txt` is not the route.**
  The yaml already points `symbol_addrs_path` there (the file does not exist
  yet; splat tolerates that). `D_80027F20 = 0x80027F20; // defined:True` does
  suppress the `undefined_syms_auto` line -- but it does **not** take the bytes
  out of the `bin` segment, so you get a duplicate definition rather than
  ownership. It is a diagnostic, not a shortcut. What that file *is* for here:
  giving a data symbol a real name, `size` or `type`, which is also the only
  correct way to rename one -- the name has to change in splat's output too, or
  the still-unowned `asm/data/*.data.s` chunk keeps referencing the old name
  and nothing defines it. `grep` the chunk before renaming anything.

* **The declared size still steers codegen elsewhere.** Nothing above changes
  the rule in `docs/addressing-and-translation-units.md`: an array's declared
  size is what picks the symbolic versus split-address access shape at a use
  site. Owning a symbol moves it from `extern` to defined *in the same unit*,
  so if a function that reads it stops matching, that is the first thing to
  look at.

mostly non-zero up to `0x8002852F`, then large mostly-zero arrays with isolated

Regenerate that list after any landing:

```sh
python3 - <<'EOF'
import re
syms = sorted(
    (int(m.group(2), 16), m.group(1))
    for l in open('splat/main.bin_undefined_syms_auto.txt')
    for m in [re.match(r'(\w+) = 0x([0-9A-F]+);', l.strip())] if m
    and 0x80027E20 <= int(m.group(2), 16) < 0x8002C000
)
for i, (a, n) in enumerate(syms):
    nxt = syms[i + 1][0] if i + 1 < len(syms) else 0x8002C000
    print('0x%08X %-14s <= 0x%X' % (a, n, nxt - a))
EOF
```

Claim them from the two edges of the owned window inward, one or a few at a
time, running §5 after each. Note that the unowned prefix
(`0x80027E20..0x80027F18`) opens on an eleven-entry table of
`{u32, void *}` pairs, two of whose pointers point back into the table itself
(`0x80027E20` and `0x80027E68`) -- `D_80027E68` is a referenced symbol in the
middle of it, so claiming that run means splitting it into two C arrays so the
second one starts at `0x80027E68`.
