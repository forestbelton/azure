# Owning an overlay's data in C

How to turn

    extern char D_80027F20[];

into

    char D_80027F20[16] = "BASLUS-00614";

and have splat, the generated linker script and the container all agree.

Everything below was measured on 2026-11-08 against `data/main/main.bin`
(sha1 `69f63236b7ab2260e2e9aa2048ce7aa540bdbe6d`) with splat 0.50.1 /
spimdisasm 1.42.4, taking `csrc/ovl_main_80020000.c` from `extern` to owning
the data objects `D_80027F18` and `D_80027F20` and the rodata object
`D_80020074`. All four containers stayed byte-identical. Re-measure rather than
trust.

> **The 0x80020000 overlay is DONE as of 2026-11-09.** Data *and* rodata: it
> owns `0x80027E20..0x8002BB6C` as one `.data` subsegment and 90 objects, and
> all 2,340 bytes of `0x80020000..0x80020924` as its `.rodata` -- see §7, which
> is now the end state rather than a queue. The incremental procedure in §4 is
> kept because it is what the *other* three overlays will need, and because §6
> is where the traps live; read §7 first if what you want is this overlay's
> shape.
>
> Three things §4 could not tell you, because all three only came up at the
> end: **why the all-zero tail could not be `.bss`** (the last bullet of §6,
> and the most surprising thing in this document), **why a string pool should
> never be owned object-by-object** (§4.7, which retired the whole of §4.6's
> `hrodata` chunk for this overlay), and **that a section boundary off the
> 4-byte grid carries three bytes of the original linker's buffer** (§4.8 --
> four of them in this project, and not one belongs to the object before it).

This is mostly about **data**, which is the hard case. Code is
`docs/landing-a-function.md`. **Rodata** needs none of the yaml work, because
splat already migrates it per symbol into the `INCLUDE_RODATA` stubs at the
foot of `csrc/ovl_main_80020000.c` -- but it has two traps of its own, both of
which cost a broken build on 2026-11-08, so it gets §4.5, §4.6 and the second
bullet of §6.

## 1. Why data is the awkward one

splat has three different stories for the three section kinds, and the
difference is the whole reason this document exists.

| section | dotted subsegment writes | per-symbol ownership? |
|---|---|---|
| `.rodata` | each REFERENCED symbol into a `asm/nonmatchings/.../*.s` listing -- and an unreferenced one **nowhere at all** | **yes** -- replace one `INCLUDE_RODATA` at a time |
| `.text` | one `.s` per function under `asm/nonmatchings/` | **yes** -- replace one `INCLUDE_ASM` at a time |
| `.data` | **nothing at all** | **no** |

Two rows to read carefully. The `.rodata` one is a trap rather than a
constraint: migration is per symbol, which is what makes rodata pleasant, but
it emits only what it can attribute to a function, so a symbol nothing
references is silently dropped from the build. §4.6 is how that happens in
practice and what to do about it.

The `.data` row is the constraint. `splat/segtypes/common/data.py`'s
`should_self_split()` returns `False` for a type that starts with a dot, and
`common/c.py`'s migration loop only ever looks at `.rodata` and `.rdata`. So a
`- [addr, .data, unit]` subsegment emits no assembly and no stub: **the C unit
must define every byte of that subsegment's span, or those bytes vanish from
the container.**

And there is exactly **one** such span per unit. `parse_subsegments()` keys
siblings by linker section (`sibling.siblings[".data"] = segment`), so two
`.data` subsegments named after the same C unit would both resolve to
`build/csrc/<unit>.o(.data)` and link the same section twice. One unit, one
contiguous owned window.

The way out is to carve the data region into **a `.data` subsegment for the
window you own and ordinary undotted `data` subsegments for the rest**. An
undotted `data` subsegment keeps getting disassembled, into
`asm/data/<name>.data.s`, which the existing `build/%.o: %.s` rule assembles
with no Makefile change. Its name has to differ from the C unit's, or splat
makes it a sibling and you are back to the double-link.

## 2. How a name gets its address

Four links in the chain. Know which one you are changing.

**`splat/main.bin.yaml`** is the only source of truth for which object owns
which address range. Everything else is generated from it.

**`build/main.bin.ld`** is generated by `splat split`. With
`ld_legacy_generation: True` it emits one input-section line per subsegment,
**in subsegment order**, grouped into the segment's `.rodata` / `.bss` /
`.text` / `.data` blocks. For the 0x80020000 overlay:

```
    ._25D000 0x80020000 : AT(_25D000_ROM_START) SUBALIGN(4)
    {
        _25D000_RODATA_START = .;
        build/csrc/ovl_main_80020000.o(.rodata);
        ...
        _25D000_TEXT_START = .;
        build/csrc/ovl_main_80020000.o(.text);
        ...
        _25D000_DATA_START = .;
        build/asm/data/ovl_main_80020000_data_pre.data.o(.data);
        build/csrc/ovl_main_80020000.o(.data);
        _25D000_DATA_END = .;
    }
```

Note that `build/csrc/ovl_main_80020000.o(.data)` was in this script **before
any of this work**, with no `.data` subsegment in the yaml at all. splat's
`auto_link_sections` inserts a generated sibling for each missing section of a
C unit and places it after the unit's text. That is why a C-defined data object
lands at the right address almost for free -- and it is also the trap: the
generated entry sits *before* any explicit `data` subsegment you add, so if you
add an undotted `data` chunk and no explicit `.data`, the C unit's data is
placed first and your asm chunk's symbols all shift. **List both subsegments
explicitly, in address order.**

**`splat/main.bin_undefined_syms_auto.txt`** is the "not owned by anything"
list -- a linker script of absolute assignments, `D_80027F20 = 0x80027F20;`,
passed with `--script=`. `write_undefined_syms_auto()` emits every symbol that
is `referenced` and not `defined`. A symbol inside any subsegment, dotted or
not, is `defined`, so adding the subsegment is what drops the line. You never
edit this file; it is regenerated on every split.

**The C file itself** decides the order. cc1psx lays `.data` objects out in the
order they are written, so **definition order is address order**. A new object
goes at its address position in the `.data` block at the foot of the unit and
nowhere else.

ROM-to-vram for this overlay: `vram = 0x80020000 + (rom - 0x25d000)`.

## 3. From a vram address to a splat offset

Everything in `splat/main.bin.yaml` is addressed by **rom offset into the
container**, never by vram. The only thing that carries a vram is the `code`
segment's own `vram:` key, and every subsegment under it gets its address
implicitly from its offset. So the first thing you do with an address like
`0x80027F18` is convert it.

The conversion is a single affine map, fixed per segment by the `start:` /
`vram:` pair at the top of that segment:

```
rom  = vram - segment_vram + segment_start
vram = rom  - segment_start + segment_vram
```

For main.bin's low overlay, `start: 0x25d000` and `vram: 0x80020000`:

```
rom = 0x80027F18 - 0x80020000 + 0x25d000
    =     0x7F18            + 0x25d000
    = 0x264F18
```

That is the number you write in the yaml, and it is also the number splat
prints in the left-hand column of every disassembly comment, which is the
cheapest way to confirm you got it right:

    /* 264F18 80027F18 7C000280 */ .word 0x8002007C
       ^rom   ^vram

The four containers each have their own map, and they are not
interchangeable -- `0x80027F18` is only an overlay address because
`main.bin`'s overlay is loaded at `0x80020000`:

| segment | `start:` | `vram:` | `rom = vram - delta` |
|---|---|---|---|
| `main.bin` option overlay | `0x21800` | `0x80088760` | `vram - 0x80066F60` |
| `main.bin` low overlay | `0x25d000` | `0x80020000` | `vram - 0x7FDC3000` |
| `main.bin` debug twin | `0x269000` | `0x80400000` | `vram - 0x80197000` |
| `town.bin` overlay | `0xb000` | `0x80088760` | `vram - 0x8007D760` |
| `dungeon.bin` overlay | `0xa3000` | `0x80088760` | `vram - 0x7FFE5760` |

Note the first three rows: `main.bin` alone has **three** different maps, so
"the `main.bin` delta" is not a thing. `0x80088760` in particular is three
different places depending on the container and, within `main.bin`, is only an
overlay address at all because of the option overlay's own map.

A one-liner, so you are not doing hex by hand:

```sh
# usage: v2rom 80027F18
v2rom() { python3 -c "print('0x%X' % (int('$1',16) - 0x80020000 + 0x25d000))"; }
```

Three sanity checks before you trust a number:

* **It must lie inside the segment.** The low overlay is
  `0x25d000..0x269000`, i.e. vram `0x80020000..0x8002C000`. An address outside
  that is not this overlay's and does not belong in this yaml at all -- see
  `docs/addressing-and-translation-units.md` on the out-of-image
  constant-base-pointer globals, which look like overlay addresses and are not.
* **The bytes must be what you expect.** `xxd -s 0x264f18 -l 0x10
  data/main/main.bin` should show the words you are about to write into C.
* **splat must already agree.** The address appears verbatim as the second
  column of the generated listing, or as
  `D_80027F18 = 0x80027F18;` in `splat/main.bin_undefined_syms_auto.txt`. If
  your computed offset's listing line shows a different vram, the segment's
  `vram:` is not the one you used.

One more place the same map shows up: the auto-generated symbol names. splat
names an unknown data symbol `D_<vram>`, so `D_80027F18` *is* its address in
hex and no conversion is needed to go the other way -- strip the `D_` and
subtract.

## 4. The procedure

Worked against `D_80027F20` at vram `0x80027F20`, rom `0x264f20`.

### 4.1 Find the object's real span

The upper bound is the next symbol's address, and the authority on where one
object ends and the next begins is splat's own disassembly. If the range is
still an undotted `data` subsegment, read its `dlabel` / `enddlabel` pairs:

    sed -n '/dlabel D_80027F18/,/enddlabel/p' asm/data/ovl_main_80020000_data_pre.data.s

If it is still a `bin` blob, read the bytes and the next referenced symbol:

    xxd -s 0x264f20 -l 0x20 data/main/main.bin
    grep -n 80027F data/../splat/main.bin_undefined_syms_auto.txt

`D_80027F20` runs to `D_80027F30`, so the span is **0x10 bytes** -- twelve
characters, a NUL, and three bytes of padding that belong to the object.

### 4.2 Move the subsegment boundary in the yaml

Carve the data region into **three** subsegments -- unowned, owned, unowned --
with the owned window in the middle and *both* neighbours undotted `data`
subsegments inside the same code segment:

```yaml
  - type: code
    start: 0x25d000
    vram: 0x80020000
    subsegments:
      - [0x25d000, .rodata, ovl_main_80020000]
      - [0x25d924, c, ovl_main_80020000]
      - [0x264e20, data, ovl_main_80020000_data_pre]    # not yet owned
      - [0x264f18, .data, ovl_main_80020000]            # owned by the C unit
      - [0x264f48, data, ovl_main_80020000_data_post]   # not yet owned
  - [0x265000, bin]
```

The trailing `data_post` chunk is not optional bookkeeping -- **it is what
keeps the segment's end on the 16-byte grid that `__romPos = ALIGN(__romPos,
16)` demands.** Leave the tail as a top-level `bin` and the segment ends
wherever your `.data` window ends, so every claim whose object does not finish
on a 16-byte boundary lengthens the container. That cost a 0x10-long build on
2026-11-08; see §6. With `data_post` running to `0x265000` the segment end is
fixed and both boundaries you move afterwards are internal to it.

The window then grows in **either** direction, one contiguous range, and
neither direction touches a segment boundary:

* **down** -- lower the `.data` start, and `_data_pre` shrinks to match.
* **up** -- raise the `.data` end, and `_data_post` shrinks to match.

Both neighbours are hand-maintained and both have to track the C file.

Shrinking a `bin` segment leaves its extracted blob behind. `OFILES` is built
from `find assets -name '*.bin'`, so the orphan keeps getting assembled into an
unreferenced object:

    rm -f assets/main/264E20.bin build/assets/main/264E20.o

### 4.3 Re-split

    splat split splat/main.bin.yaml

That rewrites `build/main.bin.ld`, the `undefined_*_auto.txt` pair and any
`asm/data/*.data.s`. It is the same command the `build/%.ld: splat/%.yaml` rule
runs, so a plain `make` would do it too.

**Do not add `--modes ld`.** It produces the linker script but *empties* both
tracked `undefined_*_auto.txt` files, because the symbol-collection pass is
skipped. **And never `rm -rf build`** -- `build/main.bin.ld` is generated and
`expected/build/` holds a stale copy. Both traps are written up in
`docs/town-sweep.md`.

`make splat` also works but wipes `asm/nonmatchings` and re-splits all four
yamls, which you do not need.

Check that splat agreed with you:

    git diff --stat splat/
    # splat/main.bin_undefined_syms_auto.txt should have LOST exactly the
    # symbols now inside the .data window, and nothing else.

### 4.4 Define it in C

At the foot of `csrc/ovl_main_80020000.c`, in address order:

```c
char *D_80027F18[2] = {
    (char *)D_80020074 + 8,
    (char *)D_80020074,
};

char D_80027F20[16] = "BASLUS-00614";
```

* **Write the size explicitly.** `[16]`, not `[]`. See §6.
* **Keep the declaration in the header** if any use site is above the
  definition -- which it almost always is, since the definition has to sit at
  its address position at the foot of the file. A header declaring a symbol its
  own translation unit defines is ordinary C, and the sized `extern` earns its
  keep: `extern char D_80027F20[16];` against a `char D_80027F20[12]`
  definition is a hard `conflicting types` error, which is one more gate for
  free.
* **Pointers are fine.** A pointer initialiser comes out as `R_MIPS_32` with
  the addend in the section, and ld resolves it to the same absolute word the
  original holds. `(char *)D_80020074 + 8` reaches the `"bu00:"` that shares
  `D_80020074`'s migrated rodata listing with `"bu10:"`; measured, both
  relocations land and the four words match byte for byte.

### 4.5 Owning a rodata symbol instead

Rodata is the easier half **as long as the symbol is referenced**. The
`.rodata` subsegment is already dotted and already migrated, every referenced
symbol already has its own `asm/nonmatchings/.../D_*.s` listing, and the
`INCLUDE_RODATA` stub in the C file already holds the symbol's address
position. You delete the stub and write the definition in its place, with no
yaml change at all:

```c
/* was: INCLUDE_RODATA("asm/nonmatchings/ovl_main_80020000", D_80020074); */
const char MEM_CARD1[8] = "bu10:";
const char MEM_CARD0[8] = "bu00:";
```

Three things that are **not** like the data case:

* **`const` is load-bearing.** Without it the object is writable and cc1psx
  emits it under `.data`, which in this overlay is at the *other* end of the
  segment. See §6.
* **Position is the stub's old line, not the foot of the file.** The `.rodata`
  objects are interleaved with the functions, in address order, exactly where
  the `INCLUDE_RODATA` calls sit now.
* **One listing can hold several objects.** `D_80020074`'s listing was two
  `.asciz` plus two `.align 2`, which is two 8-byte objects at `0x80020074`
  and `0x8002007C`, not one 16-byte one. Read the listing before choosing the
  type; `enddlabel` is where splat thinks the object ends, and §4.6 is what to
  do when splat thinks wrong.

The gate is §5 with one substitution: check `_25D000_TEXT_START` instead of the
`.data` size. It must equal the vram of the `c` subsegment,
`0x80020000 + (0x25d924 - 0x25d000)` = `0x80020924`. The C unit's `.rodata`
size is the other half of it, and it must equal the span of the `.rodata`
subsegment -- `0x25d000..0x25d0c0`, so 192.

### 4.6 Splitting one rodata object, and the symbol splat then DELETES

> **SUPERSEDED FOR THIS OVERLAY, 2026-11-09, by §4.7.** The `hrodata` chunk
> this section builds is gone: the 59 messages are string literals in the C
> unit and cc1psx emits the pool itself. What is still live here is the
> *technique* -- `slus_006.14.yaml` uses `hrodata` too, the symbol_addrs split
> is how you end an over-long `dlabel`, and the silent-deletion trap is real.
> Read §4.7 first; come back here if the strings in your case are not literals
> in an initialiser.

splat sizes a rodata object from where the next *referenced* symbol starts, so
one `dlabel` routinely covers several unrelated things. `SAVE_ICON_VRAM_RECT`
was the worst case in this overlay: a single 0x86C-byte object spanning
`0x800200B8..0x80020924`, because `set_save_icon` held its only reference. It
is really an 8-byte GPU `RECT` followed by 0x864 bytes of Shift-JIS UI
messages.

**Force the split in `splat/main.bin_symbol_addrs.txt`** (the yaml has pointed
`symbol_addrs_path` there from the start; the file need not have existed):

```
SAVE_ICON_VRAM_RECT = 0x800200B8; // size:0x8
D_800200C0 = 0x800200C0;
```

The `size` is what makes spimdisasm end the first object. Then the RECT is an
ordinary §4.5 landing -- and its type is *witnessed*, not guessed, because the
use site reads `*(RECT *)SAVE_ICON_VRAM_RECT` and walks it across three
`StoreImage` calls, so the cast can go away:

```c
const RECT SAVE_ICON_VRAM_RECT = {0x380, 0x100, 4, 0x10};  /* in the C unit */
...
    r = SAVE_ICON_VRAM_RECT;                 /* was *(RECT *)SAVE_ICON_VRAM_RECT */
```

**Now the trap, and it is silent.** Rodata migration only emits a symbol it
can ATTRIBUTE to a function. Nothing references the pool, so after the split
splat wrote those 0x864 bytes **nowhere** -- no listing, no asm file, no
warning, and a container 0x864 bytes short. The split created the symbol and
deleted the data in the same step.

The fix is the same shape as `data_pre`/`data_post`: carve the orphan out as a
subsegment of its own, which is disassembled unconditionally. Here it earns
`hrodata` rather than plain `rodata`, because the content is text:

```yaml
      - [0x25d000, .rodata, ovl_main_80020000]
      - [0x25d0c0, hrodata, ovl_main_80020000_rodata_pool]
      - [0x25d924, c, ovl_main_80020000]
```

`hrodata` (`splat/ext/hrodata.py`) seeds the file into `asrc/` **once** and
never rewrites it, so it can be turned into something readable. Since
2026-11-09 the readable form is not assembly at all: the pool lives in
`asrc/str/<name>.txt`, one entry per line, and `tools/shiftjis_to_asm.py`
generates the `.s` beside it through the `asrc/str/%.s: asrc/str/%.txt` rule.
Name the subsegment `str/<name>` so `hrodata` writes into that tree, and the
entry is just the text:

```
D_800200C0=Ｆａｉｌｅｄ　ｔｏ　ｄｅｌｅｔｅ　ｄａｔａ．
```

The default form emits the string, a NUL, then zeros to the next 4-byte
boundary -- exactly the layout all 59 entries use, so a pool converts
mechanically. Four things to know before doing the same elsewhere:

* **Two more entry forms carry the bytes that are not text.** `:nopad=` emits a
  string and its NUL and stops; `:bytes=HH HH` emits literal bytes, under a
  label or under none. Between them they cover a pointer word sitting inside a
  pool (`asrc/str/names.txt`, `D_80080A50`) and padding that is not zeros
  (`asrc/str/monsters.txt`, the last entry).
* **The value is NOT stripped, and must not be.** U+3000 IDEOGRAPHIC SPACE is
  this game's space character and Python's `str.strip()` counts it as
  whitespace. One item description ends with one; stripping it shortened the
  pool by 4 bytes and moved every later string, which is the sort of break that
  looks like a generator bug anywhere except where it is.
* **Keep the `Covers rom` line in the header.** Comment lines pass through to
  the generated `.s`, which is where `hrodata` reads the provenance back from.
  Drop the line and the only guard against the yaml moving off the file goes
  quiet -- the file still assembles, just no longer to the size the linker
  script is placing.
* **Check the padding bytes, not just the strings.** All 59 entries pad with
  zeros, which is what the default form produces -- but the three bytes after
  the LAST entry's padding, `0x80020921..0x80020924`, are `05 61 64`. Those
  belong to the section, not to the string (§4.7's last sub-section), so that
  entry would need `:nopad=` plus a `:bytes=05 61 64` line. A decoder that only
  walks NUL terminators will not notice either fact.

The gate for an `hrodata` chunk is its object's section size against the
subsegment span:

    mips64-linux-gnu-size -A build/asrc/str/<name>.o | grep '^\.rodata'
    # e.g. 2664 == 0x21268 - 0x20800 for asrc/str/monsters.txt

And because the file is frozen, **moving the subsegment in the yaml does not
move the bytes in the file.** `hrodata` records the seeded rom range in the
file's header and warns on a later split when the two disagree; that warning is
the only guard, so read it.

### 4.7 When the rodata is a STRING POOL, let cc1psx emit it

**Measured 2026-11-09. This is the better answer whenever the rodata is
string literals, and it is worth checking for before doing any of §4.6.**

The 0x864 bytes at `0x800200C0..0x80020924` were never a separate object to
own. They are the string literals of the eight `u8 *` tables in this unit's
`.data`, and cc1psx puts them at exactly those addresses by itself.

The rule in gcc 2.7.2 is: a file-scope initialiser's string constants are
**deferred**, then flushed right after that initialiser's data, in **reverse
order of first appearance**, with **duplicates merged** -- globally, so a
string first used by one table and reused by a later one is emitted once, at
the first table's position. Confirmed directly:

```c
u8 *a[2] = {"AAA", ""};
u8 *b[2] = {"", "AAA"};
```

```asm
a:  .word $LC0 ; .word $LC1
    .rdata
$LC1: .ascii "\000"        <<< reversed
$LC0: .ascii "AAA\000"
b:  .word $LC1 ; .word $LC0 <<< merged, nothing re-emitted
```

**Simulate it against the ROM before writing anything.** Walk the tables in
address order; for each, take its pool-pointer words, keep first appearances,
reverse that list; concatenate. For this overlay that predicts **all 59
addresses in the ROM's order** -- including that the empty string lands 35th
of 39 in the message table's block, because it is 5th to appear there, and that
it is emitted once for the sixty-odd entries that use it. 59 of 59 is not a
coincidence; it says the pool is these initialisers and nothing else.

Then the whole job is: write the literals into the tables, extend the
`.rodata` subsegment over the pool, delete the `hrodata` subsegment and its
`asrc/` file. No `INCLUDE_RODATA`, no named symbols, no `extern` block --
csrc/main.h lost 59 declarations and the tables stopped needing the
non-`const` hack that §6 describes, because a string literal is already
`.rdata` without the keyword.

Three things it costs:

* **The Japanese cannot stay in the source.** cc1psx has no Shift-JIS input
  encoding and `azure shiftjis` only runs on `asm/`/`asrc/` sources, never on
  what cc1psx emits, so the bytes are `\x` escapes. Put the decoded text in a
  comment on the line above and generate the two together. In this unit each
  message is a `#define MSG_... ((u8 *)"\x..")` with that comment, which is
  what makes the 20-entry message table read as the game's dialogue script.
* **The section's last three bytes are not an object, and cannot be one.**
  `.rodata` here ends at `0x80020921` -- the last message's NUL -- and the text
  starts at `0x80020924`. The three bytes in between are `05 61 64`, not zeros,
  so the linker's `FILL(0x00000000)` does not produce them and a string literal
  cannot either, since `.ascii` ends in exactly one NUL. Nor can a named
  3-byte array: cc1psx emits `.align 2` before every file-scope object, and
  `__attribute__((aligned(1)))` does not change that (both measured), so the
  array would be pushed onto `0x80020924` and the first function. A deferred
  string constant, by contrast, gets no TRAILING align -- which is the only
  reason `0x80020921` is reachable from C at all. So they are spelled as what
  they are, raw section content:

      __asm__(".rdata\n"
              "\t.byte 0x05, 0x61, 0x64\n"
              "\t.data");

  All 59 messages stay literals. §4.8 is what the bytes turn out to be.
* **Position is now implicit.** The pool lands where the tables are, so the
  tables have to come after every other `.rodata` contribution in the file.
They do, because the data block is at the foot and `const RECT
SAVE_ICON_VRAM_RECT` is the last const above it. If you reorder that block,
`.rodata` reorders with it.

The gate is §5's, plus the `.rodata` size: `size -A` must say `.rodata 2340`
against the subsegment span `0x25d924 - 0x25d000`, and `_25D000_TEXT_START`
must still be `0x80020924`.

### 4.8 The junk bytes at a boundary that does not land on 4

ASPSX/psylink pads up to the next alignment with **whatever was in its
buffer**, not with zeros. The scan below finds the ones at a SECTION end;
read the last bullet first, because the same thing happens at ordinary object
boundaries inside a section and that is the common case. Every section
boundary in this project that does not already land on 4 shows it:

| container | offset | bytes | as text |
|---|---|---|---|
| `town.bin` | `0x00C19D` | `2e 73 65` | `".se"` |
| `town.bin` | `0x00D521` | `35 2f 30` | `"5/0"` |
| `main.bin` | `0x25D921` | `05 61 64` | `"\5ad"` |
| `main.bin` | `0x26989D` | `20 42 30` | `" B0"` |

Four boundaries over two containers, found by scanning every `rodata` /
`.rodata` / `hrodata` subsegment's last word for a NUL followed by non-zero
bytes:

```sh
python3 - <<'EOF'
import yaml
for name, b, y in [('main.bin', 'data/main/main.bin', 'splat/main.bin.yaml'),
                   ('town.bin', 'data/town/town.bin', 'splat/town.bin.yaml')]:
    ROM, Y = open(b, 'rb').read(), yaml.safe_load(open(y))
    flat = []
    def walk(e):
        if isinstance(e, list): flat.append((e[0], e[1] if len(e) > 1 else 'bin'))
        elif isinstance(e, dict):
            for sg in e.get('subsegments') or []: walk(sg)
            if not e.get('subsegments'): flat.append((e['start'], e.get('type')))
    for e in Y['segments']: walk(e)
    flat.sort()
    for (o, t), (o2, _) in zip(flat, flat[1:]):
        if t not in ('rodata', '.rodata', 'hrodata'): continue
        w = ROM[o2 - 4:o2]
        if 0 in w[:-1]:
            k = max(i for i, c in enumerate(w) if c == 0)
            if k < 3 and any(w[k + 1:]):
                print(name, hex(o2 - 3 + k), w.hex(' '), bytes(w[k + 1:]))
EOF
```

Three things that follow:

* **It is a printable-ASCII fragment every time, and never the same fragment
  twice.** `05 61 64` occurs nowhere else in `main.bin`; `5/0` occurs once
  more, in the random filler. So they are off-cuts of *something* textual in
  the toolchain's own memory -- a filename, a date, a version string -- but
  **what** is not known, and nothing here identifies it.
* ~~**It is not the preceding object's padding.**~~ **CORRECTED 2026-11-13: it
  usually IS, and the scan above only finds the ones at a section end.** The
  same off-cut appears at ORDINARY OBJECT boundaries inside a section, wherever
  a string is shorter than the span up to the next 4-aligned object. The twin's
  rodata chunk has seven of them in 0x810 bytes: `02` after `"illegal data"`
  (`0x269146`), `AE` after `"card_win.c"` (`0x26962B`), `A2` after
  `"cardbk.c"` (`0x26965F`), `0C` after the card-info header template
  (`0x2697A3`), `3C` after `"cardslot.c"` (`0x2697D7`), `03` after
  `"cardsme.c"` (`0x26980A`) and `20 42 30` after `"memory.c"` (`0x26989D`) --
  the last being this table's own `main.bin` entry, which is not special after
  all. So **read the bytes up to the next object's address, not up to the
  string's NUL**, and put them in that object's initialiser:

      const char D_80400620[12] = "card_win.c\0\xAE";

  A 12-byte literal in a `char[12]` is legal C -- the NUL is dropped -- and it
  keeps the object's declared size right, which §6's last trap is about. The
  section-content spelling below is only needed when the span is NOT 4-aligned,
  which is why `0x80020921`'s three bytes need it and the twin's do not.
* **Expect it when you take over any rodata object whose string is short.**
  Not just the last one in a section.

## 6. Measured facts and traps

* **THE CODE SEGMENT'S END MUST BE 16-BYTE ALIGNED, AND THE OVERSHOOT IS
  DOUBLED AND REMOTE.** This broke the build on 2026-11-08. Claiming
  `D_80027F30` means moving the `.data` window's end to `0x264f48`, and
  `0x264f48` is 8 bytes off the 16-byte grid. splat emits
  `__romPos = ALIGN(__romPos, 16)` after *every* code segment, so:

      _25D000_ROM_END   0x264f50   should be 0x264f48   +8
      _269000_ROM_END   0x2719f0   should be 0x2719e8   +8   (the debug twin)
      built             0x275810   reference 0x275800   +0x10

  Note what the symptom is **not**. Every boundary inside the overlay was
  right -- `.rodata` 2340, `_25D000_TEXT_START` `0x80020924`,
  `_25D000_DATA_END` `0x80027F48`, `.data` 48 -- and the C was correct. The
  container was simply 0x10 bytes long, and the second 8 came from a segment
  150 lines further down the yaml that nothing in the change had touched. The
  text end obeys this same rule and the yaml already says so; what was missing
  was that it applies to the far end of the segment too.

  The fix is structural, not arithmetic: end the code segment at `0x265000`
  with a trailing undotted `data` subsegment (§4.2) so the boundary you move to
  claim an object is internal to the segment. Then alignment never enters into
  it. The alternative -- only ever claiming objects whose end happens to be
  16-aligned -- makes the queue in §7 unworkable, since most of those spans are
  0x4, 0x8, 0xC or 0x18.

* **A RODATA OBJECT MUST BE `const`, AND THE BUILD BLAMES SOMETHING ELSE.**
  This broke the build on 2026-11-08. `char D_80020074[16] = "bu10:\0\0\0bu00:";`
  compiles and its bytes are right, but a writable array goes under `.data`:

      	.globl	D_80020074
      	.data            <<< not .rodata
      	.align	2
      D_80020074:
      	.ascii	"bu10:\000\000\000bu00:\000"

  `.rodata` then came out 16 bytes short (2324 against 2340),
  `_25D000_TEXT_START` fell from `0x80020924` to `0x80020914`, **every function
  in the overlay moved down 0x10**, and the symbol itself linked at
  `0x80027F08` in the middle of the data window. What `make` reported was
  `FAIL 0x69ac of 0x275800 bytes differ (1.05%); first at 0x25d038` -- a
  function-pointer table in rodata holding `0x800210E0` where the reference has
  `0x800210F0`. The first differing byte is nowhere near the object you
  changed, and the symptom reads like a bad pointer table rather than a missing
  keyword. `const` is the whole fix.

  The declaration has to agree or it is a conflicting-types error, so
  `extern const char MEM_CARD1[16];` in `csrc/main.h`. And a non-const pointer
  table that points into it needs the cast back -- `(char *)D_80020074 + 8` --
  or you get `initialization discards 'const' from pointer target type` at
  every entry. It still builds; the alternative is making the `char **` use
  site in `format_card` const-correct, which is more churn than the cast.

  **Check the section, not just the bytes:**

      grep -n -B4 '^D_80020074:' build/csrc/ovl_main_80020000.s
      mips64-linux-gnu-size -A build/csrc/ovl_main_80020000.o | grep -E '^\.(text|data|rodata)'

  The directive you want to see above the label is **`.rdata`**, not
  `.rodata` -- that is cc1psx's ECOFF-era spelling and gas files it under
  `.rodata` in the object, which is what the linker script asks for. So the two
  commands disagree on the name by design: `.rdata` in the `.s`, `.rodata` in
  the `size -A`. Correct looks like `.rdata` / `.rodata 2340`; broken looks
  like `.data` / `.rodata 2324`.

* **cc1psx pads a data object up to its own alignment, and no further.**
  `char D_80027F20[] = "BASLUS-00614";` emits `.ascii "BASLUS-00614\000"`
  followed by `.space 3` -- 16 bytes, which is right *here* only because
  `align(13, 4) == 16`. An object whose true span is not `align(strlen+1, 4)`
  comes out short with `[]`. Write the size.

* **`data` vs `.data` is not cosmetic, and neither is the name.** Undotted
  `data` disassembles to `asm/data/<name>.data.s`; dotted `.data` writes
  nothing and hands the span to the C sibling. The undotted chunk's name must
  differ from the C unit's. This is the same dot rule as `.rodata` in the same
  yaml, seen from a third side -- the comments on all three subsegments in
  `splat/main.bin.yaml` are worth reading together.

* **One `.data` subsegment per unit.** If you need two disjoint owned ranges,
  carve the translation unit instead -- `docs/overlays.md` already has the
  nine-source boundaries (`c_server.c`, `card_mes.c`, ... `memory.c`) this
  overlay should eventually split along, and each of those units gets its own
  window. Remember `build/csrc/ovl_%.o` is the pattern rule that gives an
  overlay unit its `-G0`; a new unit outside that prefix silently gets the
  resident flags.

* **Order the subsegments explicitly.** Relying on `auto_link_sections` to
  place the C unit's `.data` works only while there is no undotted `data`
  chunk; the generated entry goes right after the text, i.e. *before* the chunk
  you wanted first.

* **`defined:True` in `splat/main.bin_symbol_addrs.txt` is not the route.**
  The yaml already points `symbol_addrs_path` there (the file does not exist
  yet; splat tolerates that). `D_80027F20 = 0x80027F20; // defined:True` does
  suppress the `undefined_syms_auto` line -- but it does **not** take the bytes
  out of the `bin` segment, so you get a duplicate definition rather than
  ownership. It is a diagnostic, not a shortcut. What that file *is* for here:
  giving a data symbol a real name, `size` or `type`, which is also the only
  correct way to rename one -- the name has to change in splat's output too, or
  the still-unowned `asm/data/*.data.s` chunk keeps referencing the old name
  and nothing defines it. `grep` the chunk before renaming anything.

* **The declared size still steers codegen elsewhere.** Nothing above changes
  the rule in `docs/addressing-and-translation-units.md`: an array's declared
  size is what picks the symbolic versus split-address access shape at a use
  site. Owning a symbol moves it from `extern` to defined *in the same unit*,
  so if a function that reads it stops matching, that is the first thing to
  look at.

* **AN ALL-ZERO OBJECT STILL NEEDS AN EXPLICIT `= {0}`, AND `.bss` IS NOT
  AVAILABLE AT ALL.** This is the one that decided the shape of the finished
  overlay. 13.8 KB of its 15,692-byte data region is zero -- work buffers the
  original source surely declared without an initialiser -- and the obvious
  spelling is the obvious one:

      u8 D_80028808[0x9C4];            /* WRONG */
      u8 D_80028808[0x9C4] = {0};      /* right */

  cc1psx emits `.comm` for the first (measured: gcc 2.7.2 has no
  zero-initialised-data-in-bss optimisation, so an explicit initialiser does
  reach `.data`, however many zeros it holds), and a `.comm` lands in the C
  object's `.bss`. **splat's generated `.bss` input-section line for a C unit
  sits between the segment's `.rodata` and its `.text`**:

      _25D000_RODATA_START = .;
      ...
      _25D000_BSS_START = .;
      build/csrc/ovl_main_80020000.o(.bss);     <<< here
      _25D000_TEXT_START = .;

  so the mistake does not shorten the data at the top of the segment -- it
  inserts the buffer at `0x800200C0` and **moves every function in the
  overlay down**, with `make` blaming a rodata function-pointer table exactly
  as the missing-`const` trap above does. `size -A`'s `.bss` line is the cheap
  check and §5 now runs it.

  And **no**, the tail cannot be turned into a real `.bss` subsegment to make
  the zeros honest. Two independent reasons:

  1. **Two four-byte runs of non-zero residue sit inside the zero region**, at
     `0x8002A98C` and `0x8002B964` (`0xF97F8BEF` and `0x6F7C7327`, high-entropy
     and read by nothing). Each is the word immediately after a buffer whose
     true length is witnessed by the word count handed to `func_8003FE78`, so
     the zeros are not one run but three, and a NOBITS section would write
     zeros over both. A unit gets one subsegment per linker section, so three
     disjoint windows cannot be expressed anyway.
  2. ~~**splat's legacy generation emits the four section groups in a fixed
     order per segment**, `.rodata` / `.bss` / `.text` / `.data`.~~
     **WITHDRAWN 2026-11-10.** The order is not fixed by the tool:
     `section_order` is a yaml option, settable per segment, and splat's own
     source notes that it is *legacy* generation which ignores it. So this is
     this repo's configuration, not a wall. Reason 1 is the one that stands,
     and it is enough on its own -- three disjoint windows cannot be one
     NOBITS section however the groups are ordered.

  While withdrawing that: the sibling claim that per-unit `.data` cannot be
  expressed at all is also wrong. A `.data` subsegment per object placement
  builds byte-identical -- measured by moving `D_8002BB08` into its own
  `csrc/main/memory_state.c` -- because legacy generation emits one
  input-section line per subsegment *in subsegment order*. What blocks the
  data carve is that the per-unit cut points are unproven and the container
  check cannot referee them; see `docs/overlays.md`, "The build CAN express
  per-unit data".

  So an overlay's zero tail is initialised data in C whether the original
  source said so or not, and the file says why where it does it.

### Where the data ends, and why `0x8002C000` was the wrong answer

The old version of this section called `0x80027E20..0x8002C000` "one
file-backed data region", because that is where the segment ends and the bytes
up there are in the container. They are **pad**, and the witness is a word
count. Every trailing buffer in this overlay is handed to `func_8003FE78`,
whose third argument is a length in words (`p = (u8 *)n + count * 4`), and
every one of those counts lands exactly on the next referenced symbol:

| buffer | words | so it ends at | next symbol |
|---|---|---|---|
| `0x800287E8` | 0x27A | `0x800291D0` | `0x800291D0` |
| `0x800291D0` | 0x112 | `0x80029618` | `0x80029618` |
| `0x80029618` | 0xF9 x 5 rows | `0x8002A98C` | (residue, then `0x8002A990`) |
| `0x8002A990` | 0x394 | `0x8002B7E0` | `0x8002B7E0` |
| `0x8002B7E0` | 0x1C | `0x8002B850` | `0x8002B850` |
| `0x8002B850` | 0x45 | `0x8002B964` | (residue, then `0x8002B968`) |
| `0x8002B968` | 0x68 | `0x8002BB08` | `0x8002BB08` |
| `0x8002BB08` | 0x19 | **`0x8002BB6C`** | nothing |

Six exact hits make the seventh trustworthy: the last object ends at
`0x8002BB6C`, the 0x494 bytes above it are zero, nothing references them, and
`0x269000` is where the container's next sector-aligned resource begins. So
they are the mastering pad, and they stay in `ovl_main_80020000_pad`.

That chunk is **not** optional bookkeeping, and the failure is not the one the
first bullet of §6 describes. The next segment's LMA is `__romPos`, not its own
`start:`, so without the pad chunk this segment ends at `0x268b6c`, `__romPos`
aligns to `0x268b70`, and the debug twin and everything after it lands early.
Measured 2026-11-09 by deleting the line:

    built 0x275370 bytes, size differs by -0x490
    FAIL  0x83a5 of 0x275370 bytes differ (1.31%); first at 0x268b70

Same rule, opposite sign to the 2026-11-08 incident: there the window's end was
8 bytes *past* the grid and the container came out long.

The same word counts are what split two buffers into "buffer + residue word"
in the C file; see the `.bss` bullet in §6.

### The town overlay has no unit oracle

§4 assumes you know which unit owns the bytes. Here you do not, and it is not
a gap that effort closes:

* **No assert records.** `docs/overlays.md` is explicit -- none of town.bin's
  85 assert records is inside this overlay; they are all in the tier-2 low-RAM
  objects. So there is no debug twin naming the original units, which is what
  gave main.bin's carve its nine.
* **No `$gp`.** The overlay is built at `-G0`, so `tools/tuscan.py`'s
  membership signal does not exist (`docs/addressing-and-translation-units.md`).
* **And the reference signal is NOISE.** Which of the three carved units
  mentions a data symbol does not decide anything, because *use is not
  definition*: 132 symbols are used only by `ovl_town.c` and 55 only by
  `ovl_town_800BF3F0.c`, and they interleave --- **83 of the first group sit
  above the first of the second, and 54 of the second sit below the last of
  the first.** No contiguous three-way assignment fits, so there is nothing to
  infer from. Do not spend an afternoon re-deriving this; the counts are the
  answer.

What is left is **link order**, which is a fact and not an inference: the
region's first bytes are emitted by the segment's first object. So the owned
window is a **contiguous prefix** and it belongs to `csrc/ovl_town.c`.

### Why a prefix, and the lever if that ever stops being enough

`ld_legacy_generation: True` makes a segment emit **one group per section
type**, and inside the DATA group splat lists every C object before every asm
data object. Checked against the card overlay's own script rather than
assumed:

```
_25D000_DATA_START = .;
build/csrc/main/c_server.o(.data);     ... the nine units ...
build/csrc/main/memory.o(.data);
build/csrc/ovl_main_80020000.o(.data);
build/asm/data/ovl_main_80020000_pad.data.o(.data);
```

So a C unit's bytes cannot sit after an asm chunk's, and §4.2's `data_pre`
window -- unowned bytes *below* the owned ones -- is not available here. The
town shape is therefore two subsegments, not three:

```yaml
      - [0x51fc0, .data, ovl_town]        # owned, grows upward
      - [0x52548, data, ovl_town_data]    # not yet owned
```

The segment still ends at the top-level `[0x7e000, bin, ovl_town_read_tail]`,
so the 16-byte-grid problem §4.2 warns about cannot arise from moving this
boundary -- it is internal.

**If a non-prefix window is ever needed**, the lever is more segments, not a
different group order: `splat/slus_006.14.yaml` splits one run across adjacent
`type: code` segments for exactly this reason ("one segment can hold only one
`.rodata` group under ld_legacy_generation"), and the same trick gives a
second DATA group. A given C object's `.data` can still only be placed once.

### One object per `dlabel`, and no merging

The nine 84-byte records at 0x800CF880 look like one 0x2F4-byte array. They are
not, and collapsing them would break the link twice over: `D_800CFB74` points
at each one separately, and **164 functions in this overlay are still asm
stubs** that reference these symbols by name. An `extern`-less `dlabel` is not
a free element -- it is a symbol something needs.

### Use the type the unit already declared

153 of the first 226 `dlabel`s already have a typed `extern` from the function
sweeps, and that type is the definition's type -- not a judgement call, and
writing a different one is a `conflicting types` error, which is the gate §4.4
describes working for you. Where the sweeps never needed a declaration, the
listing's element width is all you have, and `s32[21]` for an undeclared
84-byte record claims nothing more than that.

Watch for a symbol with **two different declarations in two units**:
`D_800D0B14` is `UnkTown2AE8 *` in one and `s32` in another. One definition
cannot satisfy both; the existing `D_800CF874_b[] __asm__("D_800CF874")` alias
in `ovl_town.c` is the shape that does.

### Two measured facts worth having

* **An explicitly zero initializer lands in `.data`, not `.bss`.**
  `u8 D_800CF828[16] = {0, ...}` is 16 bytes of `.data` under cc1psx 2.7.2 --
  verified by the window accounting, since the object is entirely zero and the
  owned window would otherwise be 16 bytes short. The `.bss` placement of zero
  initializers is a later-gcc optimisation and this compiler does not do it.
  So a zero-filled object in the region can be owned like any other, and
  `Unk80082660 D_800CF720[33] = { { 0, -1, 0, 0 } };` -- one entry written,
  32 implied -- replaces 66 lines of `.word 0x00000000`.
* **A wrong window end shows up as a RODATA difference.** Set the `.data` end
  from anything other than the last object's real end and the build fails with
  `size differs by +0x60` and `first at 0x00bf24`, which is in the overlay's
  **rodata** and looks like a rodata bug. It is not: the C object's `.data` is
  larger than the window the yaml reserved, the DATA group spills, and every
  section after it shifts. The first difference is always upstream of the
  cause. Compute the end as `0x51fc0 + (last_object_end - 0x800CF720)` and
  check it against `objdump -h build/csrc/ovl_town.o`'s `.data` size, which
  must equal the window exactly.

### The queue, as parks

`tools/decomp/datawork.py` is `worklist.py`'s job for this work and
`tools/decomp/dataverify.py` is `ovlverify.py`'s. Both read the current state
off the yaml, the listing and the unit every time they run, so neither can go
stale while a park is open.

**There is nothing to rank, which is the one way this differs from the
function sweep.** A C unit's `.data` is the region's contiguous prefix, so the
only choice is how many objects the next park takes. `--count` sets that, and
the tool prints where the runs of same-shaped objects end, which is where a
park should stop -- a park that ends in the middle of a run makes the next
one read the same shape twice.

**`dataverify.py` is a real gate and it is the reason this can be delegated.**
It compiles the candidate at `-G0`, takes the object's `.data` and compares it
against the container with relocated words masked -- no link, so no `make`,
so an agent can run it without touching shared state. It checks three things:
the bytes, the LAYOUT (each object's offset inside `.data` against its vram
delta, which is what catches a wrong array length AT the object instead of as
a mystery at the end), and the window size the yaml's next boundary must be.
It has a self-test -- the landed tranche verifies clean, 0 problems -- and a
negative test: a deliberately wrong length shows as `+0x4` layout drift on
every object after it, and FAILs.

What it cannot see is what `ovlverify.py` cannot see: a relocation against the
wrong symbol that resolves to the right word. So the brief makes the agent
read every relocation against its own listing and hand the list back, and
`make containers` is still the gate, run by whoever merges.

The park contract is the function sweep's: the agent writes to `scratch/`
under a unique prefix, hands back a re-runnable anchor-based merge script, the
object table with each type's provenance, the relocation list, and ONE yaml
number. It does not touch `csrc/`, `splat/` or `docs/`, does not run `make`,
and does not commit.

The first park is **D_800CFCA8..**, where the struct-typed objects start. All
of the next five are all-zero, so `= { 0 }` covers them and no field layout is
needed; the struct layouts only become work at `D_800CFD18`
(`UnkTownVec16[16]`). `D_800CFCF3` is the first padding case rule 7 describes
-- one declared byte with a 12-byte gap after it.

### 9.1 THE EMISSION MODEL IS NOT FILE ORDER AT -G8, AND THAT DECIDES THE FILE LAYOUT

> **CORRECTED 2026-11-13.** This section used to say `.rodata` order is file
> order. That is true of the -G0 units and false of this one, and the
> difference is what forced the rodata chunk into a second translation unit.

At -G0, `.rodata` order **is** file order, with file-scope const objects
emitted where they are defined and a function's own constants emitted where the
function is. Confirmed against the finished 0x80020000 overlay: `ASSERT_FMT` is
defined at `csrc/main/c_server.c:640` and lands at `0x80020000`, the start of
the section, because nothing earlier in that file contributes rodata; then
`FILENAME_C_SERVER` (:641), `gSwCardEventHandlers` (:643),
`gHwCardEventHandlers` (:651) follow in order, and the 24-byte gap at
`0x8002005C..0x80020074` before `MEM_CARD1` (:772) is the anonymous `$LC`
pool of the functions in between. `build/csrc/main/c_server.s` shows it
directly: `.rdata` and `.text` alternate down the file.

**At -G8 ALL FILE-SCOPE DATA IS EMITTED BEFORE ALL TEXT.** `mips_asm_file_start`
diverts the text to a temp file when `TARGET_GP_OPT` is on -- the comment in
`mips.c:4174` says why, "so that we can put all externs before all symbol
references ... for the assembler's global pointer optimizations to work" --
and `mips_asm_file_end` (`mips.c:4237`) appends it after everything the data
stream wrote. `function_prologue`/`function_epilogue` are what switch
`asm_out_file` between the two streams (`mips.c:5327`), so a *function's* own
constants, including a jump table, are in the text stream and land last.
Measured with `tools/psx272gcc -O2 -S` on

    const char A[12] = "hello";
    int f(int x) { switch (x) { /* five arms -> a jump table */ } }
    const char B[12] = "world";

    -G8:  A, B, .text, jump table      <- NOT file order
    -G0:  A, jump table, B             <- file order

So at -G8 a named object's position **within the data group** is yours to
choose, but no source ordering can put it after a compiler-emitted constant of
the same unit. That is the whole reason `csrc/ovl_main_80400000_rodata.c`
exists: the twin's `.rodata` is `[jtbl_8040007C][0x810 of objects]`, the table
is func_804016D0's, and a unit gets one subsegment per section, so the two runs
have to be two units with the yaml ordering their input sections. Defining the
objects in the function unit instead measured the right total, `.rodata` 2084,
and `main.bin` `0x79a of 0x275800 bytes differ, first at 0x26907c` -- the
table's own address.

### 9.2 AT -G8 EVERY CONST OBJECT OF 8 BYTES OR LESS GOES TO `.sdata`, AND THE ORIGINAL'S DID NOT

This is the first constraint and it has no counterpart in the 0x80020000
work, because that overlay is -G0. Measured with `tools/psx272gcc -O2 -G8`:

    void (*const PTR4)(s32 *) = callee;        -> .sdata
    const char EIGHT[8] = "bu10:";             -> .sdata
    const char *const SMALL = "10";            -> .sdata  (BOTH the pointer
                                                  and the literal)
    const char ASSERT_FMT[40] = "...";         -> .rdata
    const char VNAME[16] = "card_first_flg";   -> .rdata

It applies to anonymous string literals too, so a short format string written
at a call site lands in `.sdata` as readily as a named array. The original
compiler did not do this: there is **not one $gp-relative reference in this
block** (`docs/overlays.md`), and the 3-byte `D_804006C0` is reached with
`lui %hi` / `lh` by the landed func_80404EA0. So SN's 4.0 kept readonly data
out of the small-data section and FSF 2.7.2 does not.

The way through is an explicit section attribute, and it must name
**`.rodata`**, not `.rdata`:

    void (*const D_80400000)(s32 *) __attribute__((section(".rodata")))
        = func_8040855C;

`section(".rdata")` emits `.section .rdata,"a",@progbits`, which gas keeps as
a section genuinely called `.rdata` that the linker script never collects --
measured: `size -A` showed `.rdata 4` beside `.rodata 140`, and the container
came out 4 bytes short with the first difference at the section start. cc1psx's
own bare `.rdata` directive is the ECOFF alias and does land in `.rodata`;
an explicit `.section` is taken literally. Two consequences:

* **Every rodata object of 8 bytes or less has to be a NAMED object with that
  attribute**, so the short format strings cannot be written as literals.
  45 of the data chunk's 98 objects are in this class, and so are 27 of the
  rodata chunk's 98 -- **but the rodata chunk is a unit of its own and so is
  -G0**, where `mips_section_threshold` is zero and the question does not
  arise, so `csrc/ovl_main_80400000_rodata.c` carries no attribute at all. The
  27 are listed in its header, for whoever moves one of them back into the
  -G8 unit. (The file is -G0 because it matches the Makefile's
  `build/csrc/ovl_%.o` pattern rule and takes no target-specific override; for
  data that is a difference without a consequence, and the containers say so.)
* **Do NOT put the attribute on a `const` object.** Measured 2026-11-13: for a
  non-`const` object gcc emits `.section .data,"aw",@progbits`, and for a
  `const` one it emits `.section .data,"a",@progbits` -- the same name with
  different flags, in a file that also uses plain `.data`. A `const` object
  that belongs in `.data` should lose the `const` instead; two declarations in
  `csrc/main_twin.h` needed exactly that. (Beware when testing this: a second
  attributed object in the same file inherits the section the first one
  opened and emits no directive of its own, which can make the difference look
  like it is not there.)
* An object nothing references must also be non-`static`, or gcc discards it.
  `D_80400000` is referenced by nothing in C or in any remaining asm stub.

### 9.2b NINE OF THE DATA CHUNK'S 107 LABELS CANNOT BE OBJECTS AT ALL

The same alignment mechanism as §9.3, seen from the data side, and it is the
one thing in this region that cost real analysis. gcc emits `.align 2` before
**every** file-scope object (mips.h's `DATA_ALIGNMENT` raises an array's
alignment to a word), so a label that does not start on the 4-byte grid cannot
be declared -- the declaration would push it up onto the next word and move
everything after it. Nine of the 107 are in this class, each a byte or
halfword read inside something larger, and each has to be absorbed into the
4-aligned object above it: `D_80408ADD`, `D_80408ADE`, `D_80408ADF`,
`D_80409526`, `D_80409CAE`, `D_8040B1EE`, `D_8040B516`, `D_8040C336`,
`D_8040C43E`, `D_8040C5DE`. Nothing references any of those names. So the
region is **98 objects**, and "label" and "object" are not the same count.

Three labels run the other way, covering more than one object, and need an
extra NAME each to cover the remaining bytes -- a definition that covers
bytes, not a symbol invented to take an address: `D_80408A40[3][0x20]` (three
16-entry 5551 CLUTs after `D_80408A30`'s `UnkAnimStep[2]`; the live
`SAVE_ICON_CLUTS` has five rows, this has three), `D_80408CF8`, and
`D_80409540[0x750]`.

**THE RODATA CHUNK RUNS THE OTHER WAY ALMOST THROUGHOUT: 47 LABELS, 98
OBJECTS.** splat sizes a rodata object from the next *referenced* symbol, and
nothing in this segment refers to any of these interiors symbolically, so one
label routinely covers a filename plus everything after it -- `D_80400138` is
one 1036-byte label holding 32 separate strings. **The pointer tables in the
twin's own `.data` are the oracle**, and they are already written out as plain
address words because the rodata was unowned when they landed: `D_80408AA0`
names the two 8-byte card prefixes inside `D_804000D0`'s label, `D_80408AB8`
the six filename suffixes inside `D_804000F8`'s, `D_80408B2C[20][4]` all 31
message strings inside `D_80400138`'s, `D_80408C8C` four menu rows inside
`D_80400570`'s, `D_80408CB0` two inside `D_804005C8`'s,
`D_80408CF4`/`D_80408CF8` two inside `D_80400668`'s, and `D_804090C8` the six
slot-state names inside `D_80400800`'s. Those addresses can now become names;
doing it is a follow-up on the data block, not part of the rodata landing.

Only two of the 47 run the data chunk's way, off the 4-byte grid and absorbed
into the object above: `D_804006C2` into `D_804006C0` and `D_80400718` into
`D_80400714` (§9.5).

### 9.2c A MOSTLY-ZERO OBJECT WITH A NON-ZERO TAIL IS A DESIGNATED INITIALISER

FSF 2.7.2 accepts them -- they are a GNU extension long predating C99 -- and
it is the only reasonable spelling here:

    u8 D_8040B1D0[0x328] = {
        [0x325] = 0x01,
        0xC0,
        0xD0,
    };

emits `.space 0x325` and then the three bytes. The alternative, a separate
3-byte array, does not work: `.align 2` pushes it onto the next word (§9.2b).

**§6's warning about non-zero residue inside a zero run paid off three times**
in this region, each one word or less and each at the tail of a group buffer
where the next group's alignment begins: `01 C0 D0` at `0x8040B4F5`, `89` at
`0x8040C317`, and `3C 78 DA 42` at `0x8040C624`, which is the last word of the
whole region. Read the bytes; do not assume a long zero run is uniform.

### 9.3 THE BLOCKER: A COMPILER-EMITTED JUMP TABLE GETS `.align 3`, AND THIS ONE IS AT 0x7C

**`rodata_pre` cannot be owned without changing the stand-in compiler.** It
sits *below* `jtbl_8040007C`, so owning it puts 0x7C bytes ahead of the jump
table inside one input section -- and gcc aligns a jump table to
`BIGGEST_ALIGNMENT`:

    final.c:1516   readonly_data_section ();
    final.c:1518   ASM_OUTPUT_ALIGN (file, exact_log2 (BIGGEST_ALIGNMENT
                                                       / BITS_PER_UNIT));

guarded only by `#ifdef READONLY_DATA_SECTION`, which mips.h defines
(`:3690`), and `BIGGEST_ALIGNMENT` is 64 (`mips.h:1080`). 64/8 = 8, so
`.align 3`. The ROM puts the table at `0x8040007C`, which is 4-aligned and
**not** 8-aligned, so the original compiler used `.align 2` here.

Measured: with the seven objects owned, `.rodata` came out 148 against the
window's 144, the four extra bytes being gas's padding from 0x7C to 0x80, and
`make containers` reported `size differs by +0x4` with the first difference at
`0x269000`. `objdump -s -j .rodata` shows the gap directly.

This has never bitten before because **every other compiler-emitted jump table
in the project is at offset 0 of its unit's `.rodata`**, where `.align 3` is
free. The 4-aligned `jtbl_*` symbols elsewhere (`jtbl_8003323C` and friends)
are in PSY-Q *assembly* listings, not compiler output, so they are not
evidence either way.

There is no source lever and no flag. The options, none of them taken here:

1. **Patch the stand-in** so a jump table aligns to 4. It would affect only
   this unit, since `tools/psx272gcc` is used by nothing else, and it should
   be a no-op on everything that currently builds -- no unit in the tree has a
   compiler-emitted jump table at a non-zero `.rodata` offset. It is still a
   change to the compiler and wants its own measurement.
2. **Rewrite the `.align 3` before a jump table in this unit's generated `.s`.**
   Same effect, no compiler change, but a pipeline special case.
3. **Leave `rodata_pre` alone.** It is 0x7C bytes and 7 objects.

### 9.4 `rodata_post` IS DONE, AND IT TOOK A SECOND TRANSLATION UNIT

> **CORRECTED 2026-11-13, in the landing.** This section used to say the
> window could grow FORWARD from the jump table with every object defined
> *below* `func_804016D0` in the same C file. The second half of that is not a
> thing you can do: §9.1 is why. The first half is right -- the window does
> grow forward from `0x26907c` -- but the objects live in a file of their own.

A unit gets one `.rodata` subsegment, so an owned window has to be contiguous,
and it does not have to start at the segment start. But at -G8 a unit's
`.rodata` is `[all its file-scope objects][all its functions' own constants]`
in that order, whatever the file says (§9.1), and the twin's section runs
`[jtbl_8040007C][0x810 of objects]` with the table belonging to
`func_804016D0`. One unit cannot produce that order, and one unit cannot have
two windows. So it is two units and the yaml orders the two input sections:

      - [0x269000, rodata, ovl_main_80400000_rodata_pre]   splat's, §9.3
      - [0x26907c, .rodata, ovl_main_80400000]             the jump table, 0x14
      - [0x269090, .rodata, ovl_main_80400000_rodata]      98 objects, 0x810
      - [0x2698a0, c, ovl_main_80400000]

`csrc/ovl_main_80400000_rodata.c` is data only and needs no Makefile change --
`CFILES` is a `find` over `csrc` -- and splat's legacy generation emits one
input-section line per subsegment in subsegment order, which is the same
property §7 measured for per-unit `.data`. The live overlay's yaml already has
the shape: five `.rodata` subsegments for five units of one segment, and
`[0x265530, .data, ovl_main_80020000]` is a unit with no text at all.

**Both rodata chunks and the data chunk are DONE as of 2026-11-13** --
`.rodata` 20 for the function unit and 2064 for the data unit against the two
windows, `.data` 15432 against `0x3C48`, `.sdata`, `.sbss` and `.bss` all
absent or zero in both objects, four containers byte-identical. The data chunk
is independent of both rodata chunks, so owning it first was uneventful.

**The same device would unblock `rodata_pre`**, and it is the fourth option
§9.3 does not list: a third unit whose `.rodata` is `0x269000..0x26907c` puts
`jtbl_8040007C` at offset 0 of the *function* unit's section, where `.align 3`
is free, and the seven objects at offset 0 of their own. Not done, not
measured, and out of scope where it came up; §9.3's compiler story is still
the honest account of why it cannot be done inside one unit.

Two things learned there that belong with §4 rather than here. **The
relocation inventory of a region is worth taking before you start**: this one
is 29 words in FIVE places (`D_804089E8` 9, `D_80408A30` 2, `D_80408CFC` 11,
`D_80408D4C` 2, `D_804090E0` 5 -- the last being function pointers), and a
survey that found only three of the five would have been discovered the hard
way. And **`splat/main.bin_undefined_syms_auto.txt` did not change**, contrary
to §4.3: the nine off-grid names and `D_8040C628` are absolute-assigned there
both before and after, even while the `dlabel`s defined them. They resolve
correctly and nothing references them, so it is harmless -- but §4.3's "should
have LOST exactly the symbols now inside the window" does not hold for labels
spimdisasm could not place on a word boundary.

### 9.5 Two smaller facts, both settled in the landing

* **`D_804006C2` AND `D_80400718` ARE NOT OBJECTS, AND ONE OF THEM NEEDED A
  `size`.** Each starts off the 4-byte grid and is the tail of the object
  above: `D_804006C2` is the second half of the 3-byte `D_804006C0` that the
  landed func_80404EA0 copies with `memcpy(buf, D_804006C0, 3)` -- `lh` + `lb`,
  so splat named the `lb`'s target -- and `D_80400718` is the same thing in
  the five-byte block move of func_804053A0's park. Owning the chunk removes
  the `dlabel`s that defined them, and that is a **link failure** for any
  reference that survives: the parked func_804053A0's nonmatching listing
  still relocated against `D_80400718` and `ld` said `undefined reference`
  twice. The fix is §4.6's, `D_80400714 = 0x80400714; // size:0x8` in
  `splat/main.bin_symbol_addrs.txt`, which makes spimdisasm spell the byte
  load `%lo(D_80400714 + 0x4)` instead of inventing a name. `D_804006C2`
  needed nothing, because func_80404EA0 is compiled C and has no listing.
  Both names survive as harmless absolute assignments in
  `splat/main.bin_undefined_syms_auto.txt`, exactly as the data chunk's nine
  off-grid names do.

  **It does not clear `verify.py`'s `?` on that park, and that is a tooling
  bug, not a symbol-table one.** The mark moved from the `lb` to the `lui`:
  gas keeps a HI16/LO16 pair's addend on the LO16 only, so the built
  `lui` carries 0 where `asmlib.listing_addend` reads `+0x4` out of
  `%hi(D_80400714 + 0x4)`. Any `SYM + offset` spelling will do this. The
  remedy belongs in `asmlib.py`.

* **THE "SECTION BOUNDARY" JUNK IS AN OBJECT-BOUNDARY PHENOMENON**, and §4.8
  now says so. `0x26989D`'s `20 42 30` (`" B0"`) after `"memory.c"` is the
  last of SEVEN in this one chunk, not a one-off at the section end, and none
  of them needs §4.7's `__asm__` escape hatch: each span is 4-aligned, so the
  bytes go in the initialiser of the object above and the object keeps its
  real size.
