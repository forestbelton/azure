## The verifier is the only thing that counts

    python3 tools/decomp/ovlverify.py /tmp/claude-1000/agent-@ID@/ovl_dungeon.c func_XXXXXXXX

It prints `target N words, candidate M words, K differing`. **A function is
landed only at `0 differing` with candidate words == target words.** It takes
several function names at once; use that to re-check the whole batch cheaply.
`--raw` shows unmasked bytes (useful to prove a `%hi/%lo` the verifier masked is
really a relocation and not a constant address).

The ground truth for each function is its listing:

    asm/nonmatchings/ovl_dungeon/func_XXXXXXXX.s

Read it before writing anything. The header line `nonmatching func_X, 0xNN`
gives the byte length; /4 is the word count.

**ON ANYTHING OVER ~200 WORDS, SIZE THE RESIDUE WITH `aligndiff.py`, NOT WITH
`ovlverify`'s COUNT.** `ovlverify` compares word N against word N, so a single
TRANSPOSED pair misses twice and inflates the number: on one function this
session it reported 169 where the honest figure was 85.

    python3 tools/decomp/aligndiff.py <your copy> FUNC

aligns the two streams first. The difference decides whether you keep going or
park, so get it right before you spend context on either.

An aligndiff row is a claim about TEXT and an ovlverify word count is a claim
about BYTES. Before spending effort on a reported difference in a relocated
operand (`%hi`/`%lo`), confirm it with `ovlverify.py --raw`.

## Your first search is the unit's own comment corpus

The landed bodies in `csrc/ovl_dungeon.c` each carry a comment giving the one
spelling fact that made them land, and for a function in the same family those
comments are line-for-line templates. Two things to run before anything else:

    grep -n 'THE D_80083160 BASE IS A LOCAL OF ITS OWN' csrc/ovl_dungeon.c
    python3 tools/decomp/leverindex.py --grep <the opcode or idiom you see>

On batch j31 the typedef grep below returned **nothing usable** for either
function -- both take `u8 *`/`UnkVec *`, which is most of this block -- while
those two commands pointed straight at a measured mechanism, and the landed
`func_8008B9FC`/`func_8008C13C` turned out to be line-for-line templates for
the prologue, tail and `&D_80083460` handling of the function being written.

**THEN GREP ITS PARAMETER TYPES FOR A NAMED TEMPLATE.** `include/structs.h`'s
typedefs carry hand-written field comments, and several of them name the
resident function that reads the struct -- in prose, where no tool looks.
`provision.py` has no route that reads those comments or keys on a target's
parameter types. One such sentence was the ENTIRE landing of a 334-word
function on its first compile, after four provision.py routes returned nothing
usable. For each parameter type in the signature you have decoded:

    awk '/typedef struct UnkSlot/,/} UnkSlot;/' include/structs.h | grep -o 'func_[0-9A-F]*'

then check whether each name it prints is already landed, and read it.

**AND ON ANYTHING OVER ~400 WORDS, CONDENSE THE LISTING FIRST.** It roughly
halves what the listing costs you to read:

    sed -e 's|/\* [0-9A-F]* \([0-9A-F]*\) [0-9A-F]* \*/|\1|' \
        asm/nonmatchings/ovl_dungeon/FUNC.s | sed -e 's/  */ /g'
